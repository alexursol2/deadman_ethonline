## Any blockers? Need help?

```
Three, all on the partner side. We asked the first two in Discord and have had no reply yet,
which is the actual ask here.

1. Hedera, two things we could not exercise on testnet.

First, is the capacity saturation path reachable against testnet at all, or is a mocked HSS the
only way to test it before mainnet? Ours has only mock coverage and we say so in our limits
rather than implying otherwise.

Second, what happens when a scheduled call fires and the paying contract's balance is below the
execution cost? Is it a failed execution that consumes the schedule, or is it dropped silently?
We size a reserve that scales with the number of armed refunds, but if the underfunded case is
silent then a contract can accumulate refunds that will never fire and never report it, which
is the worst failure we can imagine on this rail.

We have four other findings from building on HIP-1215 that we believe are gaps in the stack
rather than in our code, including that network executed calls do not appear under the mirror
node's /contracts/{address}/results, so a scheduled call that fired and reverted is invisible
where any dashboard would look. All are written up in the repo and we would like them in front
of a Hedera engineer before Sunday.

2. Privy, binding a raw signing wallet.

We use a server wallet as an autonomous agent's wallet on Hedera testnet. x402 on Hedera pays
with a native TransferTransaction rather than an EVM one, so we sign through raw secp256k1Sign
over keccak256 of the transaction body. That works. What we could not do is bind it. We found
no PolicyMethod covering raw signing, and the wildcard rule that permits it also voids any
value cap sitting beside it, which we verified rather than assumed. Is that the correct
reading? Is there any other control that bounds a raw signing wallet today, at the rate,
per period volume or wallet level? And is policy support for non EVM transaction bodies
something you are looking at?

3. Blocky402 is a single vendor hard gate, unchanged from check-in #1. It is up and has behaved
correctly in every test, but it is one hosted service with no public source and no status page,
and settling through it is a track requirement. If it goes down during judging we cannot
substitute it and we fail qualification for reasons outside our control. Is there a contact, or
a fallback position?

Not blocked on anything of our own.
```

## What progress did you make since the last check-in?

```
It is live and it works end to end in public: https://deadman-server.onrender.com is the x402
endpoint and https://deadman-board.onrender.com is a live board. A real x402 payment settles
through Blocky402 into our escrow contract (0.0.10426758), the escrow arms its own refund with
the Hedera network in the next transaction, and if the seller never reveals the decryption key
the network executes that refund on its own. The refund transaction carries signatures: [],
which anyone can check on the mirror node. No keeper, no cron, nobody pushing a button.

Finished since check-in #1: the escrow contract, with 53 adversarial tests where every test
was proven to fail against a deliberately broken build before it counted; the x402 resource
server and a paying agent; and verify.ts, a buyer side tool that catches a lying seller and
names which of four commitments was broken, demonstrated against three real cheats where the
chain is happy and the seller is paid.

Privy is integrated. The agent's signing key does not exist on any machine of ours, it is a
Privy server wallet, and because x402 on Hedera pays with a native TransferTransaction rather
than an EVM one we sign it through Privy's raw secp256k1 primitive. We also report the
negative result: the spend policy cannot bind this rail, because raw signing has no policy
method and the wildcard that permits it also voids the cap. It is measured and written up
rather than glossed.

Our own adversarial suite found a real vulnerability in our contract along the way. It is
fixed and written up rather than quietly patched.
```

## Is there anything else you think we should know?

```
We would rather be judged on what we can prove than on what we claim, so the limits are on the
first screen of the README, not buried. We guarantee delivery, not correctness: a seller can
encrypt garbage, commit to its hash, and get paid. That is an oracle problem and we say so.
The refund is armed one transaction after the money lands rather than atomically, because
Hedera cannot do better today, and that is blocker 1(a). One code path, capacity saturation,
has only ever run against a mock and we label it that way instead of implying coverage we do
not have.

The README also carries a prior art table naming the closest competing designs, including
Boson Protocol's x402B and Held, which a builder from another ecosystem pointed us to this
week. In those, silence pays the seller and the buyer must dispute to stop it, or a hosted
watchdog raises the dispute for them. Ours inverts that: silence refunds the buyer, and there
is no service to run.
```
